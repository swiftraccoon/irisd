# Appendix B — Storage-layer research notes (unedited, 2026-10-31)

Research notes produced by the storage thread. Tags: verified-primary / secondary / inferred.
Summarised and adapted in `../04-storage-format.md` (the final design differs in details:
one file per elementary stream, a sidecar index instead of a `fragment` table, 24-byte trailer).

## Findings

1. **Moonfire stores raw samples + a SQLite index, in ~1-minute "recordings"; MP4 is synthesized on demand.** (verified-primary) Sample files are "simply a concatenation of the compressed, timestamped video samples… the contents of a `mdat` box"; "these files do not contain framing data… and thus are not meant to be decoded on their own." Each `recording` row (schema.sql) has `composite_id` (stream id << 32 | counter), `run_offset` (0 = first recording of an RTSP session), `start_time_90k`, `wall_duration_90k`, `media_duration_delta_90k`, `video_samples`, `video_sync_samples`, `video_sample_entry_id`, `end_reason`; `recording_playback.video_index` holds the per-frame table; `recording_integrity` holds `local_time_delta_90k`/`wall_time_delta_90k`/blake3. Sample entry (`hvcC`/`avcC` bytes) is a separate table, so a parameter-set change forces a new recording. Stated reasons for 1 minute: per-row metadata size (~4 KB/min at 30 fps), disk seeks ("16 recording streams… and 4 playback streams would cause on average 20 seeks per minute, or under 1% disk time"), 4 KiB tail waste, MP4 slice count, "on program crash or power loss, ideally it's acceptable to simply discard any recordings in progress rather than add a checkpointing scheme", and retention granularity. Recovering the last minute is an explicit non-goal. Durability order: write file → fsync file → fsync dir → insert row; delete = `garbage` row → unlink → fsync dir → drop row. H.265 recording landed in v0.7.19 (2025-01-28). https://github.com/scottlamb/moonfire-nvr/blob/master/design/schema.md , server/db/schema.sql, CHANGELOG.md

2. **Moonfire's index is 2 varints/sample; MP4 is built as moov+stbl (stts/stsz/stss, implied single-chunk stsc, co64) plus a version-1 `elst` for sub-GOP trimming; sample bytes are served as file slices.** (verified-primary) `PutVarint((Zigzag(duration_delta) << 1) | is_key); PutVarint(Zigzag(bytes_delta))`, deltas vs the previous sample of the same key/non-key class. "This does not require writing new `.mp4` files to disk… HTTP range requests… can be satisfied on `.mp4` files aggregated from several segments." mp4.rs writes `elst\x01` (64-bit) to skip from the keyframe to the requested start; media segments (fMP4 for MSE) cannot use edit lists so they start at the keyframe. https://github.com/scottlamb/moonfire-nvr/blob/master/server/src/mp4.rs

3. **Moonfire time model: NVR clock is the authority; camera clock supplies durations; drift is corrected ≤500 ppm.** (verified-primary) Units are 90 kHz since 1970 UTC. First recording of a run gets "local start time" = min over frames of (local CLOCK_MONOTONIC-anchored receipt time − preceding durations); later recordings start where the previous ended. Media duration comes from RTP deltas; `wall_duration = media_duration + clamp(local_start − start, ±media_duration/2000)`. System-clock steps mid-recording are not corrected (retroactive correction/splitting listed as future work); leap seconds assumed smeared; RTCP SRs "may be absent or late… budget cameras appear not to frequency-correct" RTP. Camera-SR-derived start time was rejected initially (5 s mismatch rule) as it could misalign streams by up to 2×threshold. https://github.com/scottlamb/moonfire-nvr/blob/master/design/time.md

4. **Apple: `hvc1` is a SHOULD, not a MUST; fMP4 is mandatory for HEVC.** (verified-primary) HLS Authoring Spec 1.5 "The container format for HEVC video MUST be fMP4"; 1.10 "You SHOULD use video formats in which the parameter sets are stored in the sample descriptions, rather than the samples. (That is, use 'avc1', 'hvc1', or 'dvh1' rather than 'avc3', 'hev1', or 'dvhe'.)"; 1.8 HDR10 SEI SHOULD be in `hvcC`; 1.13 IDR every 2 s SHOULD; 7.4 "Video segments MUST start with an IDR frame"; 7.3 tfdt MUST be continuous with the previous segment; 8.20 EXT-X-MAP MUST be present; base-type table lists `hev1` as "Use not recommended". ISO/IEC 14496-15 semantics: parameter sets "shall be stored only in the sample entry when the sample entry name is 'hvc1'" vs "may be stored in the sample entry and the samples… 'hev1'" (quoted secondhand). Apple media engineer, June 2020: "we should be able to play 'hev1' content. We do prefer 'hvc1'. If you are able to produce either, then do use 'hvc1'." Frigate's `force_record_hvc1` comment says "Apple only supports HEVC if it is hvc1" — stricter than Apple's own text. https://developer.apple.com/documentation/http-live-streaming/hls-authoring-specification-for-apple-devices ; https://developer.apple.com/forums/thread/132293 ; https://community.bitmovin.com/t/whats-the-difference-between-hvc1-and-hev1-hevc-codec-tags-for-fmp4/101

5. **HLS fMP4 rules (RFC 8216bis): `tfdt` in every traf, `mvex` in moov, movie-fragment-relative addressing (tfhd default-base-is-moof), init section must not contain samples; byte-range segments are standard.** (verified-primary) `EXT-X-BYTERANGE:<n>[@<o>]` (version ≥4) and `EXT-X-MAP` with optional `BYTERANGE` ("SHOULD contain only the Media Initialization Section", version ≥6) let a playlist point at offsets inside one on-disk file, so an HTTP server can `sendfile` ranges with no remux. `EXT-X-DISCONTINUITY` is required on timestamp-sequence changes. https://datatracker.ietf.org/doc/html/draft-pantos-hls-rfc8216bis

6. **ffmpeg defaults HEVC-in-MP4 to `hev1`; `-tag:v hvc1` writes `hvcC` with array_completeness=1 and strips in-band VPS/SPS/PPS only when the input is Annex B.** (verified-primary) isom_tags.c lists `hev1` first ("parameter sets may be in ES") then `hvc1`; movenc.c `mov_write_hvcc_tag` passes completeness for `hvc1`, and `int filter_ps = (trk->tag == MKTAG('h','v','c','1'))` feeds `ff_hevc_annexb2mp4`, which only runs when extradata is Annex B (RTSP input qualifies). Trac #10775 (reopened 2025) asks for saner defaults. https://github.com/FFmpeg/FFmpeg/blob/master/libavformat/movenc.c ; https://ffmpeg.org/pipermail/ffmpeg-trac/2025-March/073070.html

7. **Frigate does not use MKV: it records `-f segment -segment_time 10 -segment_format mp4 -reset_timestamps 1 -c copy -an` into a cache, then moves segments to `recordings/`.** (verified-primary) `MAX_SEGMENT_DURATION = 600`. Premise (c) "as Frigate uses" is incorrect; MKV (EBML, self-describing, resilient to truncation, no byte-range/HLS story, no Apple playback) is still worth listing as rejected. https://github.com/blakeblackshear/frigate/blob/dev/frigate/ffmpeg_presets.py

8. **RTP/RTCP facts.** (verified-primary) RFC 7798 §4.1: "The RTP timestamp is set to the sampling timestamp of the content. A 90 kHz clock rate MUST be used." RFC 3550 §5.1: timestamp is 32-bit, initial value "SHOULD be random", must be monotonic; §6.4.1 SR carries a 64-bit NTP timestamp ("wallclock time… when this report was sent"; sender MAY use a relative clock or zero) and an RTP timestamp that "corresponds to the same time as the NTP timestamp"; §6.2 RTCP ≈5 % of session bandwidth, minimum interval 5 s (first packet may be at half), randomized ×[0.5,1.5]. So SRs arrive seconds after PLAY, irregularly, and encode the camera's (often unsynchronized) clock. https://www.rfc-editor.org/rfc/rfc7798.html ; https://www.rfc-editor.org/rfc/rfc3550.html

9. **GStreamer's jitterbuffer (default mode `slave`) estimates sender/receiver skew with a windowed-minimum of (recv_diff − send_diff) over 2 s/512 samples, weighted average, and resets when |delta − skew| > 1 s;** `max-dropout-time` 60 s, `max-misorder-time` 2 s, `max-ts-offset-adjustment` limits per-frame slew. (verified-primary) Same spirit as Moonfire's "least delayed frame wins". https://gitlab.freedesktop.org/gstreamer/gstreamer/-/blob/main/subprojects/gst-plugins-good/gst/rtpmanager/rtpjitterbuffer.c ; https://gstreamer.freedesktop.org/documentation/rtpmanager/rtpjitterbuffer.html

10. **Retina 0.4.21 (2026-10-04, active) already unwraps RTP to i64 (`Timestamp`: jump > i32::MAX treated as backwards), tolerates non-monotonic cameras unless `enforce_timestamps_with_max_jump_secs`, and underpins Moonfire's H.265 path.** (verified-primary) It does not expose an SR→wall mapping in `Timestamp`. Camera RTP timestamps can jump when the camera's clock is set (retina#3, secondary). go2rtc: open issues #2303/#2404 (2026) report it does not emit SRs to consumers and splices new timestamp bases on re-dial — a cautionary tale, not a design to copy; MediaMTX replaces SR timestamps with server time. (secondary) https://docs.rs/retina/latest/retina/struct.Timestamp.html ; https://github.com/AlexxIT/go2rtc/issues/2404

11. **`prft` (ProducerReferenceTimeBox, 14496-12:2022 §8.16.5) maps an NTP wall time to a media time and sits before the `moof` it refers to.** (secondary — spec text quoted via a Telecom-Paris MPEG contribution; ffmpeg writes it with `write_prft`.) It makes a fragment self-describing in wall time. https://biblio.telecom-paristech.fr/cgi-bin/download.cgi?id=16608

12. **fallocate(2) mode 0 / KEEP_SIZE guarantees space and reads as zero; but on ext4/XFS it creates *unwritten* extents whose conversion on first write "can trigger numerous metadata changes and consequent journal I/O".** (verified-primary — the quote is from the Linux 6.17 notes introducing `FALLOC_FL_WRITE_ZEROES`, which is SSD-only in practice.) A 2026 ext4 series deferring unwritten splits to I/O completion measured ~25 % write gain, confirming the cost is real but modest; buffered writeback still takes a journal handle per conversion. Conversions are batched into the 5 s commit, so for 12 streams the journal traffic is tens of KB per commit. https://man7.org/linux/man-pages/man2/fallocate.2.html ; https://kernelnewbies.org/Linux_6.17 ; https://lkml.iu.edu/hypermail/linux/kernel/2601.0/02037.html

13. **ext4 extents: max 32768 blocks (128 MiB) initialized / 32767 unwritten, 4 extents inline in the inode, tree ≤5 levels; `commit=` default 5 s; `data=ordered` default; `lazytime` defers mtime/ctime writes to fsync/eviction/24 h; delete cost is proportional to extent count, so a 1 GB contiguous file is a handful of extent frees.** (verified-primary for limits/options; delete cost inferred) ext4 gained large-folio support in 6.16 ("37% improvement on a large sequential I/O workload"). https://docs.kernel.org/filesystems/ext4/ifork.html ; https://man7.org/linux/man-pages/man5/ext4.5.html ; https://man7.org/linux/man-pages/man8/mount.8.html ; https://kernelnewbies.org/Linux_6.16

14. **XFS: dynamic speculative EOF preallocation (`allocsize` fixes it; "Specifying a fixed allocsize value turns off the dynamic behaviour"), `xfs_io -c "extsize 256m"` sets a per-file/inherited-per-directory allocation hint, `fs.xfs.speculative_prealloc_lifetime` (300 s) trims unused prealloc; Dave Chinner (2011) advises dropping `allocsize` because dynamic prealloc resists fragmentation better.** (verified-primary / secondary) Both filesystems are adequate; XFS's allocation groups and `extsize` make it slightly easier to guarantee large extents under 12 concurrent writers. https://docs.kernel.org/admin-guide/xfs.html ; https://man7.org/linux/man-pages/man8/xfs_io.8.html

15. **Page-cache control: `RWF_DONTCACHE` (uncached buffered I/O) is in 6.14 core, XFS 6.15, ext4 6.17; it writes through the page cache but drops pages after writeback (Axboe: ~65 % faster and predictable than cached in his tests).** Fallbacks: `posix_fadvise(DONTNEED)` only drops clean pages ("Any unwritten dirty pages will not be freed… call fsync(2) or fdatasync(2) first"); `POSIX_FADV_NOREUSE` is a no-op before 6.3; `sync_file_range` "does not flush disk write caches" and is "extremely dangerous" for integrity. `O_DIRECT` needs block-aligned buffers/lengths (STATX_DIOALIGN since 6.1), "does not give the guarantees of the O_SYNC flag", and should not be mixed with buffered reads of the same file — a bad fit for serving recent footage from cache. (verified-primary) https://kernelnewbies.org/Linux_6.14 ; https://kernelnewbies.org/Linux_6.15 ; https://man7.org/linux/man-pages/man2/posix_fadvise.2.html ; https://man7.org/linux/man-pages/man2/sync_file_range.2.html ; https://man7.org/linux/man-pages/man2/open.2.html

16. **SQLite WAL + `synchronous=NORMAL`: "WAL mode is safe from corruption… but… A transaction committed… might roll back following a power loss"; syncs happen only at checkpoints, so a checkpoint thread keeps writers from ever blocking on fsync; default autocheckpoint 1000 pages (~4 MB); WAL grows unboundedly under checkpoint starvation; WAL does not work over network filesystems.** (verified-primary) rusqlite 0.41.1 (2026-10-28) is current. https://www.sqlite.org/pragma.html#pragma_synchronous ; https://www.sqlite.org/wal.html

17. **Alternatives: redb 4.4.0 (2026-10-13, very active, pure-Rust B-tree, ACID), fjall 3.1.13 (2026-10-25, LSM — write-amplifying by design, wrong fit), sled stuck at 1.0.0-alpha.124 (2024-10, last push 2026-04).** (verified-primary via crates.io/GitHub) None offers SQL, ad-hoc queries, `sqlite3` CLI inspection, or the `fsck`-ability Moonfire relies on; redb is the only credible alternative and buys nothing at 3–10 writes/s.

18. **io_uring in Rust: `io-uring` 0.7.15 (2026-09-07, actively maintained by tokio-rs), `monoio` 0.2.4 (crate 2024-08 but repo active, last commit 2026-10-15), `tokio-uring` 0.5.0 (2024-05; last commit 2025-07-07, 99 open issues; README still says "very young"), `glommio` 0.9.0 (2024-03; last commit 2025-04).** (verified-primary) At 3–6 MB/s in ~1 MB fragments the write path is ~5–10 syscalls/s; io_uring saves nothing measurable (inferred). Its only real benefit here would be non-blocking `fsync`/`fallocate` without a thread, which a dedicated blocking writer thread per disk already gives. Linux 6.17 (2025-09-28) io_uring additions (TX timestamps, vectorized send, multishot recv caps, mock files, uring_cmd copy avoidance) are network-side; the 6.17 items that matter are ext4 uncached I/O, `FALLOC_FL_WRITE_ZEROES`, and "Improve read ahead size for rotational devices". https://crates.io/crates/io-uring ; https://github.com/tokio-rs/tokio-uring ; https://kernelnewbies.org/Linux_6.17

19. **HDD write size and spin-down.** (inferred + local observation) Under buffered I/O the kernel merges writeback into requests up to `max_sectors_kb` (4096 KiB on the dev host's SATA disks), so application write size matters less than fsync cadence and avoiding interleaved small syncs; I found no primary block-size sweep — plan to measure with fio (`--bs=64k..4M --rw=write`). WD Purple is rated 180 TB/yr, 300k load/unload cycles, 24×7 (datasheets, secondary); continuous recording makes spin-down impossible without an SSD staging tier, and the cycle budget argues against it anyway.

20. **Timescale/64-bit.** (secondary — ISO 14496-12 from memory, consistent with Moonfire's `elst v1`) Use 90000 in `mdhd`; 32-bit (version 0) `mvhd/mdhd/tkhd/elst` durations overflow at 2^32/90000 ≈ 13.26 h, so use version-1 boxes; `tfdt` v1 is 64-bit; `trun` per-sample durations are 32-bit (fine).

21. **Rust MP4 tooling: `mp4` 0.14.0 (2023-08) and `mp4parse` (2023-05) are stale; `mp4-atom` 0.17.0 (2026-10-30, kixelated) is active; Moonfire hand-writes boxes.** (verified-primary)

## Recommended format for irisd (as proposed by this thread)

**Choice: (b) fragmented MP4 on disk, one `moof+mdat` per GOP, with a tiny recovery trailer, plus a SQLite index on SSD.** Versus (a): the same zero-copy serving (segments are byte ranges) but the file is self-describing in sizes, durations, keyframes *and* wall time (`prft`), so the index is rebuildable by a linear scan after any crash, and `ffprobe`/`ffmpeg -i` open it directly. Overhead ≈ 96 + 8·N bytes of `moof` + 32 `prft` + 16 trailer per GOP ≈ 550 B per 0.3–2 MB (0.03–0.2 %). (c) MKV and (d) plain MP4 lose byte-range HLS and (d) is only valid after `moov` is written at close.

**Byte-level layout** (`/var/lib/irisd/video/<cam>/<main|sub>/<YYYY-MM-DD>/<HH>.mp4`, rotated hourly or at 2 GiB, whichever first; also rotated on run change or parameter-set change):
```
ftyp  major 'iso6', compat 'iso6' 'cmfc' 'hvc1'                    ~24 B
moov  mvhd v1 (timescale 90000, duration 0) · trak{tkhd v1, mdhd v1 ts=90000,
      hdlr 'vide', minf{vmhd, dinf, stbl{stsd: 'hvc1'+'hvcC'(VPS/SPS/PPS,
      array_completeness=1), empty stts/stsc/stsz/stco}}} · mvex{trex}  ~700 B
repeat per GOP:
  prft v1  ref_track=1, ntp_timestamp=NVR UTC of IDR's first RTP packet,
           media_time=tfdt                                          32 B
  moof     mfhd(seq u32, monotonic per stream) · traf{tfhd(default-base-is-moof,
           default_sample_flags) · tfdt v1 (u64, 90 kHz, continuous in run) ·
           trun(data_offset, first_sample_flags, N×{u32 dur, u32 size})}   96+8N B
  mdat     N access units, 4-byte length-prefixed NALs; VPS/SPS/PPS/AUD
           stripped (kept in hvcC); SEI kept
  free     'IRIS' magic, u32 crc32c(prft..mdat), u32 fragment_len       16 B
```
Init segment = bytes `[0, moov_end)`; HLS media segment k = byte range of `prft..mdat` (trailer excluded) with `EXT-X-MAP BYTERANGE`; export = init + ranges, with a v1 `elst` added to a fresh `moov` for sub-GOP start, and `EXT-X-DISCONTINUITY`/new init at run or `hvcC` boundaries. Dahua in-band parameter sets are compared against the current `hvcC` per IDR; a change seals the file.

**SQLite schema (WAL, `synchronous=NORMAL`, on SSD, checkpoint thread, `journal_size_limit`):**
```sql
camera(id PK, name UNIQUE, ...);  stream(id PK, camera_id, kind 'main'|'sub', url);
sample_entry(id PK, sha256 UNIQUE, width, height, codec TEXT, hvcc BLOB);
run(id PK, stream_id, started_us, wall_minus_media_us, cam_sr_offset_us, end_reason);
segment(id PK, stream_id, run_id, sample_entry_id, path, wall_start_us, wall_end_us,
        media_start_90k, init_len, durable_len, bytes, state);     -- one per file
  INDEX(stream_id, wall_start_us)
fragment(segment_id, seq, offset, len, media_time_90k, duration_90k, wall_us,
         n_samples, flags, PRIMARY KEY(segment_id, seq)) WITHOUT ROWID;
event(id PK, camera_id, kind, wall_start_us, wall_end_us, retain_until_us, data);
  INDEX(camera_id, wall_start_us)
```
`fragment` is ~47 M rows / ~3 GB at 12 streams × 2 s GOP × 90 d; if that is too much, replace it with a fixed-size `frag_index BLOB` per segment written via incremental blob I/O (`zeroblob` + `Blob::write_at`) or a sidecar `.idx`; the `moof`s remain ground truth either way.

**I/O policy:** one blocking writer thread per disk (no io_uring); buffer a whole GOP in RAM (≤ ~2 MB/stream), write it with one `pwritev2(..., RWF_DONTCACHE)` (6.17 ext4/XFS; fallback: buffered + `fadvise(DONTNEED)` after sync); `fallocate(KEEP_SIZE)` in 256 MiB steps when < 64 MiB remain; `ftruncate` to length at seal. `fdatasync` each open file every 5 s, staggered across streams, then one batched SQLite transaction updating `durable_len`/fragments; power-loss window ≤ 5 s + one GOP per stream. Seal: fsync file + directory, `state=sealed`. Retention: unlink oldest sealed segments not covered by `event.retain_until_us` when free space < threshold; FIFO churn in multi-GB units keeps fragmentation bounded (verify with `filefrag`/`xfs_bmap` in a soak test). Mount ext4 `noatime,lazytime` (default `commit=5`) or XFS with `extsize=256m` inherited on the video root. Startup recovery: for each `segment` with `state=writing`, scan from `durable_len`, validate trailer CRC + `mfhd` sequence continuity, re-insert fragments, truncate at the first bad fragment. No spin-down.

**Timestamp model:** per stream, unwrap RTP to i64 (Retina); `media_time = rtp − run_base` is continuous across hourly files within a run (so HLS needs no discontinuity at file boundaries) and resets with `EXT-X-DISCONTINUITY` on reconnect. Wall time per fragment = NVR `CLOCK_REALTIME` at receipt of the IDR's first packet minus a configurable latency estimate (~50 ms), stored in `fragment.wall_us` and `prft`; search and retention use wall time only; playback inside a run uses media time with Moonfire's ≤500 ppm clamp applied at fragment boundaries. RTCP SR NTP↔RTP offsets are recorded in `run.cam_sr_offset_us` for diagnostics and main/sub (later audio) alignment, never as the search key. If |wall − (prev_wall + media_delta)| > 2 s (system clock step, camera reboot), seal the segment and start a new run.

## Open questions
- Will AVFoundation accept byte-range fMP4 segments that span the 16-byte `free` trailers (needed for multi-GOP segments), or must every segment be exactly one `prft+moof+mdat` range? Test on iOS before freezing the trailer design.
- `prft` placement/semantics verified only via a secondary quote of 14496-12; confirm against the 2022 text and that ffprobe/Apple tolerate it.
- Do the target Dahua models emit RTCP SRs, how soon after PLAY, and is their NTP sane? Measure; also confirm they emit VPS/SPS/PPS before every IDR and whether they ever change SPS without a reconnect. *(Answered for cam1 in 01: SRs every 5 s, NTP sane within 100 ms, parameter sets before every IDR.)*
- ext4 vs XFS: run a multi-week FIFO soak at 12 streams and compare extent counts and unlink latency.
- `RWF_DONTCACHE` from Rust: needs `pwritev2` via `libc` (flag 0x80); check `nix`/`rustix` support and the ext4 6.17 behaviour on partial-page tails.
- `fragment` table size (rows vs packed blob) — decide after measuring real GOP sizes. *(Decided: sidecar index.)*
- Apple spec recommends 6 s segments (7.5–7.6, SHOULD); decide whether playlists coalesce three 2 s GOPs per segment (ties into the trailer question).
- Not verified: Moonfire's on-disk sample filename scheme (believed to be the hex `composite_id`); the exact ISO text for `free`-box placement; any primary HDD block-size sweep.
